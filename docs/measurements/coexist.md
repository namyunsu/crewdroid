## Accepted at 56/60 (2026-10-29)

The target was 10/10 for every case. a, b, c and e reached it; d and f stayed at 8/10 over two attempts, and the user accepted 56/60 as the shipped state. The 4 failures are the API 31 clone running out of guest memory while Maestro's driver starts (low-memory kill of `dev.mobile.maestro`, or adbd dropping the host link on an order-4 allocation failure), see the last rows of the cause table and ADR 0007; no crewdroid command was running at those moments. Known limit for users: Maestro flows on an API 31 clone with the default 768 MB fail about 3 % of the time next to crewdroid or alone; use API 34 / 36 or `up --ram 2048` for Maestro-heavy flows. The code from attempt 2 (helper, `screen`, `check-coexist.mjs`) is what shipped.

## Cause (T66)

Android registers one UiAutomation client at a time. The on-device helper (T52), `uiautomator dump` (crewdroid's fallback and mobile-mcp's `mobile_list_elements_on_screen` with `MOBILEMCP_LEGACY_ROBOT=1`) and Maestro's driver (`dev.mobile.maestro.test` instrumentation, held for the whole flow) all need it.

## Fix (T66)

- The helper takes UiAutomation per request and releases it right after (`idleMs` 0; `-e idleMs N` keeps the old hold). No connection at start, so `up` no longer races mobile-mcp. `up` still starts the helper process (it only listens).
- When the connect fails for 1 s (another client holds it), the helper answers 503 and exits; the host treats 503 like "not answering": it uses the shell path (`input`, `uiautomator dump`) and then starts a fresh helper. Exiting is the only reliable reset found for the stuck connection.
- `screen` while UiAutomation is held: `via: "fallback"`, `nodes: []`, and `busy` says why (no tree exists without UiAutomation; focus and `png` still work). `tap --text` says the same instead of "no match". `tap x y`, `swipe`, `key` and ASCII `type` work through `input`; non-ASCII `type` exits 1 and says the helper is busy. Every fallback result carries `fallbackReason`.
- The API 31 black-screen check reads the PNG (`exec-out screencap -p`, about 70 KB instead of 10 MB) and decides from its scanlines (`isBlackPng`). A frame that cannot be read means "not black" with a stderr line, never a failed `screen` / `shot`. No raw frame is pulled anywhere now.
- A failed `uiautomator dump` looks up its own "already registered" line in logcat (from the dump's start time on), so `screen` reports `busy` instead of failing when the helper is not there either. Checked by hand: helper stopped, a 25 s Maestro flow running, `screen` -> exit 0, `busy` set, Maestro passed.
- The black-screen recovery skips the home activity (`cmd package resolve-activity` for HOME): on ATD it is black by design and is never the ADR 0005 bug.
- The helper's host port is fixed per emulator below the OS ephemeral range (`6800 + port - 5554`, e.g. 6826 for emulator-5580; any free port only if that is taken). In the fourth run, while Maestro waited for its driver, the helper logged a `Broken pipe` request every second: Maestro picks its driver port from the ephemeral range, where our forward also was, so its polls likely reached the helper [inferred; the ports were not recorded]. Forwards are now recorded with every failure.

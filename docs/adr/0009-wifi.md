# 0009 Wi-Fi·모바일 데이터 — ATD 에 Wi-Fi 가 있다, 기본은 한 번에 한 대만 주소를 받는다 (`up --wifi` 면 모든 기기)

- 날짜: 2026-10-29 · 상태: 실측 근거 있음 (T63, API 31/34/36)
- 결정: google_atd 이미지(API 31/34/36) 모두 에뮬레이터 기본 Wi-Fi 접속점 "AndroidWifi" 에 붙는다. 이미지 교체·다운로드 없이 `crewdroid net` 에 Wi-Fi 상태를 더한다.
  - `net <serial> wifi|cellular|both|none`: 켤 링크(`svc wifi`, `svc data`). 끄는 쪽을 먼저, 켜는 쪽을 나중에(T45 교훈).
  - `net <serial> handover [--to wifi|cellular] [--during <ms>]`: 기본 네트워크를 다른 링크로 옮긴다. `--during 0`(기본) = 새 링크가 붙은 뒤 옛 링크를 끈다(Wi-Fi 범위를 벗어나며 데이터로 넘어가는 폰). `--during N` = 옛 링크를 끄고 N ms 동안 링크 없음, 그다음 새 링크를 켠다.
  - `net <serial> metered on|off`: `cmd wifi connect-network AndroidWifi open [-m]` 로 Wi-Fi 를 종량제로 다시 저장한다(Wi-Fi 가 한 번 다시 붙는다).
  - 고른 링크는 기기 속성 `debug.crewdroid.link` 에 남는다(재부팅하면 사라짐). `slow` 는 Wi-Fi 만 고른 상태면 wlan0 에 같은 `tc` qdisc 를 걸고, 아니면 예전처럼 Wi-Fi 를 끄고 셀룰러(eth0)만 느리게 한다. `flaky` 는 고른 링크만 껐다 켠다. `nodata`·`airplane` 은 예전 그대로, `online` 은 둘 다 켜고 고른 링크를 지운다.
  - 모든 설정 명령은 `dumpsys connectivity` 를 다시 읽어 `transport: {default: wifi|cellular|none, connected, metered}` 를 돌려준다. 앱 쪽 확인은 프로브 `--es check transport` → `CrewProbe TRANSPORT wifi|cellular|none metered=<bool>` (ConnectivityManager 의 활성 네트워크).
- 기동 플래그·AVD 설정·`KNOBS` 는 바꾸지 않았다.
- 확인: `node scripts/check-wifi.mjs` (기본 = API 36 한 대; `--api 31` / `--api 34` 로도 실행) — 세 API 모두 wifi·cellular·both·metered on/off·slow-on-Wi-Fi·handover 두 방향·잘못된 호출 거부가 PASS, 마지막 줄 `OK: wifi, cellular, handover and metered claims hold`. 그 뒤 `node scripts/check-net.mjs` (2대) 도 `OK: all net claims hold` [확인함 2026-10-29 실행]. 유휴 비용은 `docs/measurements/features.md` T63 행.

## 이미지가 보여 주는 것 (실측)
| | API 31 | API 34 | API 36 |
|---|---|---|---|
| `ip link` | eth0, wlan0, hwsim0 | eth0, wlan0, hwsim0 | eth0, wlan0, hwsim0, thread-wpan |
| `ro.boot.qemu.virtiowifi` | 1 | 1 | 1 |
| `/sys/class/ieee80211` | phy0 | phy0, phy1 | phy0, phy1 |
| 부팅 직후 `cmd wifi status` | `Wifi is disabled` | `Wifi is connected to "AndroidWifi"` | enabled (클론 여러 대일 때 미연결) |
| 셀룰러 | `MOBILE[HSPA]` on eth0 10.0.2.15 | `MOBILE[HSPA]` on eth0 | `MOBILE[NR]` on eth0 |
| Wi-Fi | `svc wifi enable` 뒤 `WIFI` on wlan0 | `WIFI` on wlan0 10.0.2.17 (`ServerAddress 10.0.2.2`) | `WIFI` on wlan0 10.0.2.16 |
| 앱이 보는 transport | TRANSPORT_WIFI / TRANSPORT_CELLULAR | 같음 | 같음 |
| `cmd wifi connect-network ... -m` | 됨 (metered=true) | 됨 | 됨 |

`radio0` 인터페이스는 없다. Wi-Fi 는 virtio-wifi(wlan0)이고 셀룰러 모뎀 데이터는 eth0 로 나간다. 두 링크 모두 같은 slirp 대역(10.0.2.x)이라 호스트 `10.0.2.2` 는 어느 링크로도 닿는다.

## 한계: Wi-Fi 주소는 한 번에 한 대
`up --count 2` 이상이면 대부분 한 대만 Wi-Fi 주소를 받는다. 나머지는 `WIFI CONNECTING` 에서 멈추고 `DhcpClient: Broadcasting DHCPDISCOVER` 만 되풀이한다.
- 근거: API 36 클론 2대에서 5580 이 DISCOVER 를 보내는 동안 5582 의 로그에 `Received packet: 02:15:b2:00:00:01 OFFER, ip /10.0.2.17` (5580 의 MAC 앞으로 온 응답이 5582 에 도착), 5580 의 wlan0 링크 로컬 주소는 `dadfailed` (다른 클론과 같은 주소). 혼합 3대(31/34/36)에서도 34 만 붙었다(두 번 따로 띄워 두 번 다). 한 대만 띄우면 세 API 모두 붙는다. 모든 Wi-Fi 를 끄고 한 대만 다시 켜도 안 붙었다(실행 중 기기끼리의 주소 충돌이 아님). 프레임워크 재시작(`makeDistinct` 와 같은 `stop; start`)만 한 한 대는 붙었다(재시작이 원인 아님) [확인함 2026-10-29 실행, 호스트에 `netsimd.exe` 하나가 qemu 3개 옆에 떠 있었다].
- 원인: 에뮬레이터들이 netsimd 하나(호스트 프로세스)를 공유 Wi-Fi 매체로 쓰는데, 한 스냅샷의 `-read-only` 클론들은 virtio-wifi 장치 MAC 이 같다 [추론: 게스트에서 wlan0 MAC 을 바꾸고(`makeDistinct`), `connect-network -r none` 으로 MAC 랜덤화를 꺼도 그대로였다. 에뮬레이터 `-help` 에 정확히 이 경우용 `-wifi-mac-address` 옵션이 있다: "This option only applies to situation where AVD is loaded from snapshot using read-only mode"].
- 지금 동작: 여러 대에서 `net wifi|both` 는 120 s 안에 Wi-Fi 가 안 붙으면 이유(이 ADR)를 담아 exit 1 한다. 셀룰러·`online`·`slow`·`nodata`·`airplane`·`flaky` 는 영향 없다(`online` 은 기본 네트워크만 본다).
- T74 (2026-10-30, 사용자가 `-wifi-mac-address` 만 허용): 클론마다 포트에서 만든 MAC(`02:15:b2:00:15:cc` = 5580, `:ce`, `:d0`)을 줬다. 게스트 wlan0 MAC 은 바뀌었지만(makeDistinct 의 게스트 MAC 덮어쓰기도 빼 봤다) 혼합 3대(31/34/36)에서 여전히 34 만 Wi-Fi 주소를 받았다. 나머지는 AP 에 붙은 뒤 `CTRL-EVENT-BEACON-LOSS`, DHCPDISCOVER 만 되풀이. 그래서 이 플래그는 넣지 않았다 [확인함 2026-10-30 실행].
- 진짜 원인: netsimd 로그 `wifi/medium.rs: Insert station with client id 1000|1003|1006, hwsimaddr: 02:15:cc:00:00:00, Ieee80211 addr: 02:15:b2:00:15:cc|ce|d0`. netsim 의 공유 Wi-Fi 매체는 스테이션을 hwsim 주소로 구분하는데, 그 주소는 세 클론 모두 `02:15:cc:00:00:00` 이고 `-wifi-mac-address` 는 wlan0(Ieee80211) 주소만 바꾼다. 같은 hwsim 주소로 나중에 붙은 클론이 앞 클론의 자리를 덮는다 [확인함 2026-10-30 netsimd 로그 `%TEMP%/netsimd/netsim_stderr.log`].
- 고쳐지는 것(시험만, 넣지 않음): `-feature -WiFiPacketStream` (netsim 대신 에뮬레이터마다 따로 도는 Wi-Fi) 를 더하면 혼합 3대 모두 `net wifi` → `default wifi` (3.2~14 s), `-wifi-mac-address` 없이도 됐다(세 클론 wlan0 이 모두 `02:15:cc:00:00:00` 인데도). 유휴 3대 RAM 3229 MB / CPU 46.3 % (같은 방법의 기준 3144 MB / 42.9 %, +2.7 %) [확인함 2026-10-30 실행]. 다른 기동 플래그라 T74 범위 밖 — 넣으려면 사용자 결정이 필요하다. 클론끼리 같은 Wi-Fi 망에 있지 않게 되는 차이가 있다(지금도 주소를 못 받으니 잃는 것은 없다) [추론].
- T74 재시도 (2026-11-01, 사용자가 `-read-only` 클론에만 `-feature -WiFiPacketStream` 허용): 기능은 된다, 유휴 RAM 이 기준(+5 %)을 넘어 넣지 않았다.
  - 된 것: 혼합 3대(31/34/36) 새로 띄우기 4번 연속(측정 3번 + verify 1번) 모두 `net wifi` → `default wifi`, 프로브 `TRANSPORT wifi metered=false`, Wi-Fi 만 켠 채 호스트 `10.0.2.2` 로 1 KB 업로드 저장됨, `ping -I wlan0 10.0.2.2` 응답. 스냅샷은 매번 로드됐다(에뮬레이터 로그 `Successfully loaded snapshot 'default_boot'`), 부팅 평균 48.7 → 44.6 s (같은 날 같은 방법, 바뀌지 않음). `check-net.mjs`·`npm test` 도 통과 [확인함 2026-11-01 실행, `node scripts/check-wifi.mjs --count 3`].
  - 막힌 것: 유휴 3대 RAM (새로 띄우고 120 s 뒤 30 s, emulator+qemu working set) 플래그 없이 2520·2567·2495·2476·2732·2584 = 평균 2562 MB, 플래그 넣고 2662·3274·2548·2769·2820·2749 = 평균 2804 MB, **+9.4 %** (중앙값 +8.5 %, 번갈아 잰 3쌍 +11.8·+3.2·+6.4 %). 10-30 의 +2.7 % 는 한 번 잰 값이었다. netsimd(플래그 없을 때만 뜸, 약 19 MB)는 두 쪽 다 안 셌다 [확인함 2026-11-01 실행].
  - 클론끼리 Wi-Fi 로 닿는가: 안 닿는다. 클론마다 따로 된 망이라 wlan0 주소가 겹친다(10.0.2.16 또는 .17, 같은 실행에서 두 대가 같은 주소). 다른 클론 주소로 `ping -I wlan0` 은 `+2 errors, 100% packet loss` [확인함 2026-11-01 실행]. API 31 이 다른 주소에도 0.1 ms 응답을 받은 경우가 있는데, 호스트를 거치는 게이트웨이 응답(0.4~0.6 ms)보다 빨라 그 에뮬레이터 안에서 답한 것으로 본다 [추론]. 지금(플래그 없음)도 한 대만 주소를 받으므로 클론끼리 Wi-Fi 통신은 원래 안 됐다.
  - macOS·Linux 에서는 이 플래그를 시험하지 않았다 [모름].
  - 그래서 "한 번에 한 대" 문구는 그대로 둔다. 넣으려면 사용자 결정이 필요하다: RAM +9.4 % 를 받아들이거나, 기본 끔 + 켜는 옵션(`features.md` 규칙: +5 % 넘으면 opt-in).
- **결정 (2026-11-01, 사용자): 켜는 옵션.** `up --wifi` (MCP `up` 입력 `wifi: true`) 일 때만 `-read-only` 클론의 `-feature` 목록에 `-WiFiPacketStream` 을 더한다 (`src/snapshot.ts` `emulatorArgs`). 옵션이 없으면 기동 인자는 전과 바이트 단위로 같다 (`test/snapshot.test.ts`). 기본 AVD·`prepare`(스냅샷 만들기)·`KNOBS`·AVD 설정은 그대로, `-wifi-mac-address` 는 넣지 않는다. `run --wifi`·시나리오 필드는 여러 대 Wi-Fi 가 필요한 시나리오가 생길 때 더한다.
  - 기본: Wi-Fi 주소는 한 번에 한 대. `up --wifi`: 기기마다 받을 수 있다, 유휴 RAM +9.4 % (위 측정, 다시 재지 않음).
  - 놓치는 경우 (2026-11-01~02, Windows, 혼합 3대 `check-wifi --count 3 --wifi` 11번 = 기기 33대): 31대가 `net wifi` 로 Wi-Fi 를 받았고 2대(둘 다 API 34, 서로 다른 실행)가 120 s 안에 못 받았다. 놓친 기기는 `cmd wifi status` = `Wifi is enabled` / `Wifi is not connected`, wlan0 `NO-CARRIER ... state DOWN`, 연결된 네트워크 없음: AP 에 아예 붙지 않았다 (DHCP 이전 단계) [확인함 2026-11-01 실행, `check-wifi --diag` 가 남긴 기기 상태]. 왜 안 붙는지는 [모름]: logcat 에 스냅샷 이후의 Wi-Fi 줄이 없었다.
  - 그래서 `net wifi|both` 는 30 s 안에 Wi-Fi 가 안 붙으면 `cmd wifi connect-network AndroidWifi open` 을 한 번 더 보내고 나머지 90 s 를 기다린다 (결과에 `wifiRetry: true`). 이 재시도 뒤 연속 3번 통과했지만 그 3번에서 재시도가 실제로 쓰인 적은 없다 (모든 기기 4~14 s 에 붙음), 그러니 재시도가 놓침을 고치는지는 아직 [모름] [확인함 2026-11-02 실행, `node scripts/check-wifi.mjs --count 3 --wifi` 3번 연속]. T83: `node scripts/check-wifi-retry.mjs` 가 저장된 AndroidWifi 를 `cmd wifi forget-network` 으로 지워 재시도 경로를 억지로 태우면 `wifiRetry: true` 로 Wi-Fi 에 붙는다 (API 34, 38.2 s) [확인함 2026-11-02 실행]. 이것은 관찰된 실패(wlan0 NO-CARRIER)가 아니라 만든 상황이므로, 2/33 놓침은 원인 [모름] 그대로이고 고쳤다고 주장하지 않는다. 재시도는 Wi-Fi 를 종량제 아님으로 다시 저장하므로, 30 s 를 넘긴 경우에만 `metered on` 을 다시 해야 한다.
  - `up --wifi` 의 클론은 저마다 따로 된 Wi-Fi 망에 있다: 클론끼리 Wi-Fi 로 닿지 않고 wlan0 주소가 겹칠 수 있다. macOS·Linux 에서는 시험하지 않았다.
  - 실패 메시지는 기기 상태를 따른다 (T83, `src/net.ts` `wifiHint`): `up --wifi` 는 기기에 게스트 속성 `debug.crewdroid.wifi=1` 을 남긴다. 그 표시가 없으면 `up --wifi` 로 띄우라고 알려 주고, 있으면 재시도 뒤에도 못 붙었다고 알리며 `net` 을 다시 하거나 다시 띄우라고 한다. 재시도가 없는 `handover`·`slow`·`metered` 에서 `--wifi` 기기는 어느 안내도 받지 않는다.
  - 확인: `node scripts/check-wifi.mjs --count 3 --wifi && node scripts/check-net.mjs && npm test`.

## 핸드오버 중 업로드 (실측)
Wi-Fi 만 켜고 `slow`(1 Mbit/s) 로 2 MB 업로드를 시작, 3 s 뒤 `handover --to cellular`: 세 API 모두 프로브가 `UPLOAD fail SocketException: Software caused connection abort` 를 찍고 서버에는 0건이 남았다(두 번 저장되지 않음). 옛 링크의 TCP 연결은 끊기므로 앱이 다시 보내야 한다 — 그게 앱 재시도·멱등 키를 시험할 조건이다.

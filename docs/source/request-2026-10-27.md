# crewdroid 개선 요청서

Oct 27, 2026 · @윤수

**목표: AI 에이전트로 Android 앱을 만드는 개발자가 Android Studio 에뮬레이터 대신 crewdroid를 쓰게 만든다.** 지금 crewdroid는 에뮬레이터를 띄우는 비용(준비 약 8초, RAM 1.4GB)은 해결했지만, AI가 화면을 보고 누르는 반복은 스크린샷 방식보다 2.3배 느리다. 아래 순서대로 처리한다.

## 우선순위 한눈에

작업 1·2가 바이브코딩 사용자에게 직접 체감되는 개선이다. 3은 신뢰의 바닥, 4·5는 동시성 판정을 내 앱에 쓰게 하는 작업이다.

| 순서 | 작업 | 해결하는 불편 | 목표 수치 |
| --- | --- | --- | --- |
| 1 | 화면 읽기·조작 helper | AI가 보고 누르는 반복이 느림 | `screen`·`tap`·`type` 회당 0.5초 이하 |
| 2 | `layout` 검사 명령 | UI 어긋남을 캡처로 일일이 확인 | 아무 APK에 명령 1줄로 기종×글자 크기 검사 |
| 3 | CI·배포 정리 | 버전 불일치, 회귀 미검출 | main 푸시마다 CI 통과, npm·`package.json` 버전 일치 |
| 4 | `run` 일반화 | 동시성 시나리오가 데모 앱 전용 | 내 앱의 Maestro 흐름으로 `run` 실행 |
| 5 | 프록시 기반 `judge` | 서버에 `/export`·버전 이력 필요 | 서버·앱 수정 없이 중복·유실·덮어쓰기 판정 |

## 작업 1: 화면 읽기·조작 helper

**현재 병목은 `uiautomator dump`다.** 탭·입력 때마다 화면 전체 구조를 새로 뽑아 회당 3초 이상 걸린다. 같은 작업 전체가 트리 방식 23.9초, 스크린샷 방식 10.3초다.

| 단계 | 트리 방식(현재) | 스크린샷 방식 |
| --- | --- | --- |
| 화면 읽기 | 3.55초 | 0.87초 |
| 탭 | 3.27초 | 0.29초 |
| 입력 | 4.40초 | 0.82초 |
| 작업 전체 | 23.9초 · 9,695토큰 | 10.3초 · 6,212토큰 |

**요구사항**

1. 한글 입력용 on-device helper(T52)를 접근성 서비스로 확장해, 화면 트리를 상주 상태로 유지하고 요청 즉시 응답한다.
2. `screen`, `tap --text/--id`, `type --into`가 `uiautomator dump` 대신 helper를 쓴다. helper가 없으면 기존 방식으로 자동 대체한다.
3. `screen` 출력을 줄인다: 화면에 보이는 요소만, 필요한 필드(text, id, bounds, clickable)만. 현재 회당 약 2,800토큰.
4. `logs` 기본 출력도 줄인다. 현재 회당 약 3,800토큰.

**기대효과**

- 이름으로 누르는 정확성을 유지하면서 스크린샷 방식보다 빨라진다.
- "Android Studio 에뮬레이터보다 AI가 빨리 돌리는 도구"라고 말할 근거가 생긴다.

**선결조건**

- 접근성 서비스 자동 활성화가 API 31·34·36 ATD 이미지에서 adb로 되는지 확인.

**완료 기준**

- `scripts/bench-agent.mjs` 재측정에서 트리 방식이 시간·토큰 모두 스크린샷 방식보다 적다.
- `screen`·`tap`·`type` 회당 평균 0.5초 이하.

## 작업 2: `layout` 검사 명령

**검사 로직은 이미 있다. 데모 앱 전용 스크립트(`scripts/check-layout.mjs`)라서 사용자가 못 쓸 뿐이다.** 기종 5종 × 글자 크기 3단계로 줄바꿈, 화면 밖 요소, 색 대비를 잡는다.

**요구사항**

1. `crewdroid layout <serial> <pkg>` 명령과 같은 이름의 MCP 도구를 만든다.
2. 패키지명·Activity·검사 대상 화면을 인자나 Maestro 흐름으로 받는다. 데모 앱 하드코딩(`PKG`, `EXPECT`)을 제거한다.
3. 기본 매트릭스: 기종(`s24ultra`, `fold5-cover`, `fold5-main`, `flip6-cover`, `trifold-main`) × 글자 크기(1.0, 1.3, 2.0). 인자로 변경 가능.
4. 검출 항목: 버튼·라벨 줄바꿈, 잘림, 화면 밖으로 밀려 스크롤로도 닿지 않는 요소, 요소 겹침.
5. 결과는 `--json`과 exit code. 문제가 있는 조합만 스크린샷을 첨부한다.

**기대효과**

- AI가 캡처를 한 장씩 보지 않고 "어느 기종·글자 크기에서 어느 버튼이 깨졌는지"를 한 번에 받는다.
- 바이브코딩 용도에서 다른 도구에 없는 차별점이 된다.

**선결조건**

- 작업 1 helper가 있으면 30개 조합 검사 시간(현재 약 10분)이 크게 줄어든다. 작업 1 이후 진행 권장.

**완료 기준**

- 데모 앱이 아닌 임의 APK 1개 이상에서 명령 1줄로 검사가 끝난다.
- 일부러 깨뜨린 레이아웃을 검출하고, 정상 레이아웃은 통과시킨다.

## 작업 3: CI·배포 정리

**CI 파일이 `ai/work` 브랜치에만 있어 main에서 한 번도 돌지 않았다.** npm에 올라간 버전은 0.1.0인데 `package.json`은 0.2.0이다.

**요구사항**

1. CI 워크플로를 main에 올린다: `npm test`, `tsc --noEmit`, 스킬 문서 형식 검사.
2. KVM이 되는 Linux 러너에서 에뮬레이터 1대로 최소 검증(`up` → `install` → `launch` → `screen` → `down`)을 돌린다.
3. 태그 푸시 시 npm 배포까지 자동화하고, npm·`package.json`·`plugin.json`·`server.json` 버전을 일치시킨다.

**기대효과**

- 회귀가 자동으로 잡히고, macOS/Linux 지원 표기에 근거가 생긴다(T43).
- 외부에서 보는 "관리되는 프로젝트" 신호.

**선결조건**

- 없음. 다른 작업과 병행 가능.

**완료 기준**

- main 푸시마다 CI가 돌고 통과한다.
- `npx crewdroid --version`이 저장소 버전과 같다.

## 작업 4: `run` 일반화 (Maestro 흐름)

**`src/scenario.ts`에 데모 앱 정보가 하드코딩돼 있어 내 앱으로 `run`을 돌릴 수 없다.** 패키지명 `PKG`, `.SampleReceiver`, 브로드캐스트 `dev.crewdroid.sample.*`, outbox 경로, 로그 태그 `CrewProbe`가 박혀 있다.

**요구사항**

1. 시나리오 JSON에 기기별 동작을 정의할 수 있게 한다: Maestro 흐름 파일, intent, adb 명령 중 택일.
2. "대기열이 비었다"의 판정을 앱 내부(`/data/data/.../outbox`)가 아니라 **서버로 나가는 요청이 N초 동안 없음**으로 바꾼다. 작업 5의 프록시를 그대로 쓴다.
3. 기존 probe 앱 시나리오는 예제로 유지한다.
4. 계획의 FR-36(Maestro 흐름으로 `run`)을 sweep보다 앞으로 당긴다.

**기대효과**

- 개발자가 이미 가진 Maestro 흐름을 그대로 여러 기기·네트워크 조건에서 돌린다.
- 앱에 테스트용 리시버를 심을 필요가 없어진다.

**선결조건**

- 대기열 판정은 작업 5 프록시가 필요하다. 작업 4·5는 함께 설계한다.
- `adb root`·`run-as` 없이 동작해야 한다(릴리스 빌드 대응).

**완료 기준**

- 데모 앱이 아닌 앱 1개의 Maestro 흐름으로 3대 `run`이 끝나고 판정 결과가 나온다.

## 작업 5: 프록시 기반 `judge`

**최종 상태만으로는 중복·덮어쓰기를 원리적으로 못 잡는다.** DB에 unique 제약이 있으면 중복은 409로 버려져 안 보이고, 덮어쓰기는 이력이 남지 않는다. 그래서 지금 `judge`는 서버에 `/export`, `acks` 테이블, `baseVersion` 쓰기 이력을 요구한다. 소스를 JSON·URL·DB 쿼리로 넓혀도 이 한계는 그대로다.

**요구사항**

1. crewdroid가 에뮬레이터와 서버 사이에 기록용 HTTP 프록시를 띄운다. 에뮬레이터의 서버 주소(`10.0.2.2:<port>`)를 프록시로 향하게 한다.
2. 모든 요청·응답을 기기 serial, 시각과 함께 기록한다.
3. 기록을 근거로 판정 규칙을 추가한다.
   - 중복: 같은 내용(또는 같은 idempotency key)이 두 번 성공 응답을 받음
   - 덮어쓰기: 같은 리소스에 대한 PUT/PATCH 두 개가 같은 원본 버전 기준으로 둘 다 성공
   - 유실: 보낸 요청이 실패한 뒤 재시도 없음
   - 대기열 비움: N초 동안 요청 없음(작업 4에서 사용)
4. 기존 `/export` 방식은 고급 옵션으로 유지한다.

**기대효과**

- 서버와 앱을 고치지 않고 내 앱 + 내 서버에 바로 꽂아 판정한다.
- README 첫 문장 "judges the result"가 사실이 된다.

**선결조건**

- HTTPS 서버면 에뮬레이터에 프록시 CA를 설치해야 한다. ATD 이미지에서 시스템 CA 설치 가능 여부 확인.
- 리소스 식별 규칙(URL 패턴, 버전 필드 위치)을 설정 파일로 받는다.

**완료 기준**

- 번들 샘플 서버를 수정하지 않고 `BUGGY=1`에서 중복·덮어쓰기를 검출, 정상 서버에서 통과.

## 정리 작업

기능은 바꾸지 않고 신뢰도를 올리는 작업이다. 작업 1\~5와 병행한다.

- [ ] **README 비교표 재측정:** 기본 `google_atd` AVD 3개와 다시 비교한다. 현재 표는 `google_apis` 대비라 RAM·디스크 차이의 상당 부분이 이미지 차이다. 유휴 CPU(3대 약 600%)도 표에 그대로 둔다.
- [ ] **"Built for agents" 문구 정리:** 속도 주장으로 읽히지 않게 절 제목·문구를 JSON·MCP·exit code 중심으로 다듬는다. 작업 1 완료 후 속도 수치를 추가한다.
- [ ] **ATD 제약 표기:** Play 스토어·FCM·지도·카메라가 필요한 앱은 검증할 수 없다고 README 요구사항 절에 적는다. 한글 입력(T52)과 API 31 검은 화면 자동 복구는 "지원됨"으로 갱신한다.
- [ ] **에뮬레이터 버전 고정:** 검증한 emulator·이미지 버전을 README에 명시하고, `setup` 시 버전이 다르면 경고한다. 우회 코드(`AI NOTE` 약 50개)가 의존하는 동작을 CI 최소 검증으로 감시한다.
- [ ] **`.ai-log` 추적 해제:** 공개 저장소에서 내부 autopilot 로그 5개 파일을 제거하고 `.gitignore`에 추가한다.
- [ ] **저장소 크기:** 데모 mp4/gif를 줄이거나 릴리스 자산으로 옮긴다. 현재 18MB.

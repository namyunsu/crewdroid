# crewdroid 개발 방향

## 1. 핵심 메시지

> **AI가 안드로이드 앱의 화면만이 아니라, 화면 너머의 원인까지 본다.**

| 스크린샷·트리 기반 도구가 주는 것 | crewdroid가 추가로 주는 것 |
|---|---|
| 지금 화면에 무엇이 있는가 | 앱이 **왜** 죽었는가 (`triage`: 크래시·ANR·종료 사유) |
| 버튼을 눌렀는가 | 기기가 **정말 그 상태인가** (`net`·`env`·`fold` 설정 후 재확인) |
| 화면에 "저장됨"이 떴는가 | 서버에 **실제로 무엇이 남았는가** (`judge`: 중복·누락·덮어쓰기) |
| 한 번 재현됐는가 | **같은 조건을 다시 만들 수 있는가** (seed 기반 재현) |

- 비교 대상은 안드로이드 에뮬레이터가 아니다. **mobile-mcp, Appium, 스크린샷 기반 computer use**다.
- "접근성 트리를 준다"는 차별점이 아니다. README·피치에서 이 주장을 앞세우지 않는다.


### 1-1. 경쟁 분석과 포지셔닝 (2026-10-27 기준)

| 도구 | 규모 | 강점 | crewdroid가 비어 있는 자리 |
|---|---|---|---|
| mobile-mcp (mobile-next) | 약 6.9k stars | iOS·Android·실기기·클라우드까지 하나의 API. 접근성 트리 우선 + 스크린샷 폴백. 32개 도구, 크래시 로그 포함 | 네트워크 장애 주입·다기기 동시 시나리오·서버 판정 없음 |
| DroidRun / mobilerun | 약 9.8k stars | 자연어로 기기를 조작하는 LLM 무관 에이전트 프레임워크 (Python) | 테스트·판정 도구가 아니라 "폰 조작 에이전트" |
| Maestro MCP | Maestro 공식 | 에이전트가 화면 계층을 읽고 YAML flow를 작성·자기수정, CI에서 재사용 | 네트워크 조건·병렬 다기기·화면 크기 매트릭스 언급 없음 |
| Android Studio Agent Mode / Journeys | Google 공식 | 기기에 배포·화면 확인·스크린샷·Logcat 확인, 자연어 E2E 테스트, 크래시 분석 | 연결된 기기 1대 중심. 다기기·네트워크·서버 검증 없음 |
| Appium MCP | 약 500 stars | 안정적 로케이터 생성, Java/TestNG 테스트 코드 생성, iOS·Android | 단일 세션 중심, 조건 주입·판정 없음 |

아무도 안 하는 것 = crewdroid의 자리

1. 여러 기기를 동시에 띄우고 기기마다 다른 네트워크 장애를 주입하는 것
2. 버전 × 화면 × 글꼴 매트릭스를 로컬에서 무료로 일괄 판정하는 것
3. 앱 화면이 아니라 서버 데이터로 정합성을 판정하는 것

포지셔닝: "Maestro와 mobile-mcp가 앱을 조작하면, crewdroid는 조건을 만들고 결과를 판정한다." 대체재가 아니라 보완재로 간다. 두 커뮤니티의 사용자가 그대로 잠재 사용자가 된다.

Phase 2 벤치 비교 조건: "crewdroid vs mobile-mcp" 가 아니라 **"mobile-mcp 단독 vs mobile-mcp + crewdroid"**. 붙였을 때 성공률이 올라간다는 것을 보여준다.

## 2. 원칙

1. **증명 전에는 주장하지 않는다.** README의 모든 숫자는 측정 JSON에 근거하고, 측정 OS·조건을 명시한다.
2. **목표 미달은 숫자 그대로 보고한다.** BLOCKED 규칙 유지.
3. **남의 앱에서 돌아가야 의미가 있다.** 검증은 자체 데모 앱이 아니라 공개 오픈소스 앱으로 한다.
4. **새 DSL을 만들지 않는다.** 앱 조작은 Maestro flow(YAML)를 그대로 받는다.
5. **공개 저장소에서 깨끗하게 개발한다.** 숨기지 말고 정리한다.
6. **핵심 단계는 사람이 리뷰한다.** 무인 오토파일럿은 측정·반복 작업에만 쓴다.

## 3. 단계별 로드맵

### Phase 0. 신뢰 회복 (반나절)

| 구분 | 내용 |
|---|---|
| 요구사항 | `.ai-log/` 추적 해제 + `.gitignore` 등록 · README에서 "트리가 스크린샷보다 낫다" 문장 삭제 · 모든 숫자를 ready 기준 + 측정 OS 명시로 교체 · npm **0.2.0** 배포(버전 되돌리기 금지) |
| 저장소 | 공개 `crewdroid`에서 개발 재개. `crewdroid-dev`는 아카이브. 오토파일럿은 `ai/*` 브랜치에서 작업하고 main에는 의미 있는 메시지로 squash merge만 |
| 완료 기준 | 공개 레포 첫 화면에 과장·작업 로그·PC명이 없음. npm 버전 = `package.json` 버전 |
| 기대효과 | 방문자가 "AI가 뽑다 만 레포"로 판단하고 나가는 것을 막음 |

### Phase 1. 내 앱에 쓰기: `run` 일반화 (1~2주, 사람 리뷰 필수)

| 구분 | 내용 |
|---|---|
| 요구사항 | `run`이 **Maestro flow YAML**을 입력으로 받아 N대 기기에서 서로 다른 타이밍·네트워크 스케줄로 실행. 샘플 앱 하드코딩(`PKG`, `SampleReceiver`, `/files/outbox`) 제거. 앱 상태 확인은 로그 패턴·`screen` 텍스트 대기로 대체 |
| 선결조건 | Maestro CLI가 crewdroid 기기(`emulator-<port>`)에 붙는지 확인 |
| 검증 | 공개 오픈소스 앱 1개에 오프라인 업로드 시나리오를 돌려, 버그 서버에서는 위반 검출·정상 서버에서는 통과 |
| 완료 기준 | 앱 코드 수정 없이 기존 Maestro flow만으로 동작. "내 앱에 쓰는 법" 문서 1장 |
| 기대효과 | 처음 온 사람이 자기 앱에 바로 써볼 수 있는 유일한 경로가 생김 |

### Phase 2. 핵심 주장 증명: 성공률 벤치 (1주)

| 구분 | 내용 |
|---|---|
| 요구사항 | 공개 안드로이드 앱 1~2개에 버그 10개를 심음 (특정 API/화면에서만 크래시, 오프라인 후 중복 업로드, 폴드 시 상태 유실, 권한 거부 시 멈춤 등). 같은 모델·같은 프롬프트로 **mobile-mcp 단독 / mobile-mcp + crewdroid** 비교 (1-1 참고) |
| 측정 항목 | **해결 성공률**(주 지표), 소요 시간, 토큰. 조건당 최소 3회 반복 |
| 기존 작업 처리 | T52~T54(트리 경량화·상주 도우미·한글 입력)는 이 벤치의 개선 수단으로 흡수 |
| 완료 기준 | 결과 표와 원시 로그를 `docs/measurements/`에 공개. 지더라도 그대로 공개 |
| 기대효과 | README 첫 화면과 출시 글의 근거가 되는 표 하나 확보 |

**판단 기준:** crewdroid가 성공률에서 명확히 이기지 못하면 Phase 4(출시)로 가지 않는다. 지는 버그 유형을 분석해 도구를 고치고 다시 잰다.

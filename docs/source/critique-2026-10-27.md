# crewdroid 레포지토리 분석

Oct 27, 2026 · @윤수

**한 줄 평:** "AI 에이전트가 쓰는 헤드리스 안드로이드 에뮬레이터 군단"이라는 아이디어와 측정 습관은 좋지만, 핵심 기능인 다중 사용자 시나리오(`run`)가 **번들된 샘플 앱 전용**이라 지금 상태로는 남의 앱에 바로 쓰기 어렵습니다. 3일(10/23\~27) 동안 AI 오토파일럿으로 146커밋을 찍은 **데모 단계 프로젝트**입니다.

대상: [namyunsu/crewdroid](https://github.com/namyunsu/crewdroid) (main, 커밋 751b407)

## 좋은 점

- **문제 정의가 날카롭다.** "버튼을 같은 ms에 누르는 게 아니라 재시도·오프라인 큐·늦은 수정이 겹칠 때 동시성 버그가 난다"는 관점(ADR 0002)이 맞고, 중복 업로드·누락·lost update를 서버 데이터로 판정하는 구조가 실무적이다.
- **`judge`는 단독으로 쓸 만하다.** `unique` / `count` / `noLostUpdate` 세 규칙을 JSON으로 정의하고, 내 API의 export(JSON)에 그대로 돌릴 수 있다. 코드 70줄 남짓으로 단순·명확하다.
- **네트워크 장애 주입을 제대로 팠다.** 에뮬레이터 콘솔의 `network speed`가 실제 게스트 트래픽을 안 늦춘다는 걸 직접 재고 `tc netem`으로 우회했다. 3초 연속 유지될 때까지 기다리는 `settle`, 기기별 seed로 재현되는 `flaky` 스케줄도 좋다.
- **에이전트 친화 설계가 일관된다.** 모든 명령에 `--json`과 종료코드, 설정 후 상태 재확인, CLI와 MCP가 같은 함수를 공유한다.
- **안전장치가 있다.** `emulator-<port>`만 건드리고 USB 실기기는 무시, `down`은 `crew-*`만 종료한다.
- **수치를 원시 JSON으로 남긴다.** 디스크 24.7→7.0 GiB, RAM 8.45→3.93 GB처럼 주장마다 측정 근거가 있다.

## 부족한 점

- **`run`이 내 앱을 못 돌린다.** `scenario.ts`에 probe 앱의 패키지명, `SampleReceiver` 브로드캐스트, `/files/outbox` 경로가 하드코딩되어 있다. README의 "What it finds" 표 전체가 사실상 샘플 앱 + 샘플 서버(`BUGGY=1`) 데모다. 내 앱에 쓰려면 같은 테스트 훅을 심거나 시나리오 엔진을 새로 짜야 한다.
- **스스로 잰 벤치가 셀링포인트를 반박한다.** README는 "스크린샷 대신 접근성 트리"를 장점으로 내세우지만 `agent-bench.json`에서 트리 방식이 더 비싸다(아래 표).
- **"부팅 \~7초"는 과장에 가깝다.** 같은 출력의 `readySeconds`가 약 40초다. 실제로 쓸 수 있는 시점은 40초.
- **무겁다.** 3대 유휴 CPU가 약 600%(6코어). 일반 개발 노트북에서 3대 이상은 부담.
- **한글 입력이 안 된다.** `type`은 ASCII만 지원해 한국 앱 폼 테스트에는 IME를 따로 설치해야 한다.
- **테스트·CI가 얇다.** 단위 테스트 약 47개는 주로 파서·인자 검증이고, 실제 검증은 에뮬레이터가 필요한 `scripts/check-*.mjs` 40여 개에 의존한다. `.github` 워크플로 없음.
- **크로스플랫폼은 주장만 있다.** 측정은 전부 Windows 11 PC 한 대. macOS/Linux는 `platform.ts`로 분리만 되어 있고 실측 근거가 없다.

## 허접한 점

- **공개 레포에 AI 작업 로그가 그대로 있다.** `.ai-log/friction.md`에 "옛 세션 PID 28620이 T15 점유 → shift 빈손 종료"가 수십 줄 반복되고, `heartbeat-NYS-Desktop.md`처럼 개인 PC명이 드러난 파일도 커밋되어 있다. 외부인이 보면 신뢰도를 깎는 노이즈.
- **버전이 엇갈린다.** `package.json`은 0.2.0, npm 배포본은 0.1.0. README 배지를 보고 설치하면 문서와 다른 버전을 받는다.
- **커밋 히스토리가 지저분하다.** `docs: progress`, `brief(auto)`, `Merge ai/work into main (autopilot auto-ship)`이 대부분이라 사람이 변경 이력을 추적하기 어렵다.
- **본체보다 주변이 크다.** 핵심 `src`는 약 3,100줄인데 데모 GIF·MP4·히어로 렌더러·측정 문서·ADR이 그보다 훨씬 많다. 마케팅 자산에 비해 제품이 덜 익었다.

## 앱 개발자에게 실제 효용

| 대상 | 효용 | 이유 |
| --- | --- | --- |
| 백엔드 동시성 검증만 필요한 경우 | **중상** | `judge`·`hammer`는 기기 없이 독립적으로 사용 가능 |
| 오프라인 동기화·업로드 큐가 있는 앱 | **중간** | `net` 기기별 장애 주입 + `judge` 서버 검증 조합은 쓸 만함. 단, 시나리오 구동은 직접 짜야 함 |
| Claude Code·Cursor로 안드로이드를 디버깅하는 개발자 | **중간** | `triage`, `env`, `app`, `fold`를 MCP로 바로 호출 가능 |
| 일반 앱 개발자(UI·기능 테스트) | **낮음** | Maestro, Espresso, mobile-mcp 대비 확실한 이점이 없고 한글 입력 불가 |

**결론:** 지금은 "완성된 테스트 도구"가 아니라 **좋은 아이디어의 작동하는 데모**다. 남에게 권하려면 최소한 세 가지가 필요하다.

1. `run`을 임의 앱에 연결할 수 있게 일반화 (앱 액션을 시나리오 JSON에 정의)
2. `.ai-log` 정리 및 커밋 히스토리 정돈
3. npm 배포 버전을 `package.json`과 일치
